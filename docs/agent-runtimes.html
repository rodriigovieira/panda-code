01The short answers

Three questions, up front:

QuestionAnswer
Do we use -p for Claude? yes Every section is headless claude -p. There is no interactive TUI in a section.
Do we use stream-json output? yes And stream-json input too — the process stays alive across turns and we write prompts as JSON to its stdin.
For Codex, is it just app-server? yes, exclusively Since 2026-07-30. The old codex exec --json path and every flag builder behind it were deleted, not flagged off.

The asymmetry is not an accident of history — it is the best transport each vendor exposes. Claude Code's richest programmatic surface is headless stream-json over stdio. Codex's is a persistent JSON-RPC server. We took the best one on each side rather than forcing a common shape, and paid for that with one mapping layer.

02Claude: -p plus stream-json in both directions

A Claude section is a plain child_process.spawn — not a PTY — built by buildStreamClaudeCommand (apps/desktop/src/main/index.ts:572):

claude -p \
  --input-format stream-json \
  --output-format stream-json \
  --verbose \
  --include-partial-messages \
  --include-hook-events \
  --replay-user-messages \
  --append-system-prompt "<TL;DR instruction>" \
  [--resume <sessionId>] [--model …] [--permission-mode … | --dangerously-skip-permissions] [--effort …]

The input side is the part people miss. Because we pass --input-format stream-json, the process does not exit after answering; it sits on stdin waiting for the next turn. A prompt is one line of JSON:

{"type":"user","message":{"role":"user","content":"run the tests"}}\n

Output is read from stdout, split on newlines, and each line handed to parseStreamJsonLine. There is no ANSI, no cursor addressing, no screen scraping. The renderer never sees a terminal — it sees a list of typed conversation items.

Why this over a PTY The ExecutionMode type still carries a legacy "terminal" value, but every code path that creates a section now hard-codes "stream-json". A PTY would have meant parsing a UI built for humans, and — fatally for this product — it would have given the phone nothing to render. The relay ships conversation items, not bytes. Structured output is what makes the mobile companion possible at all.

03Every flag on the Claude command line, and why

FlagReason it is there
-pHeadless. The section is driven by our UI, not by a human at a terminal.
--input-format stream-jsonKeeps one process alive across many turns. Without it every prompt costs a fresh spawn and a --resume.
--output-format stream-json + --verboseThe event stream. --verbose is required to get the full per-event detail rather than a summary.
--include-partial-messagesToken-level deltas → text streams into the bubble instead of appearing in one block at the end.
--include-hook-eventsHook activity is real work the user is waiting on; hiding it makes the app look hung.
--replay-user-messagesThe user's own prompt comes back through the same stream. That gives one authoritative ordering for the transcript, so the optimistic local bubble can be reconciled instead of guessed at.
--append-system-promptCarries the TL;DR instruction — the model writes the recap, we do not post-process for it.
--resume <id>Re-attach to the same Claude session after the process exits (or after a model switch).
--dangerously-skip-permissionsOnly substituted when the requested mode is bypassPermissions: headless Claude refuses --permission-mode bypassPermissions at runtime, so the launch flag is the sole path. The UI gates it behind Face ID.

The user's own typed command is not discarded — streamCompatibleCommandParts tokenizes it and keeps an allow-list of flags that survive into the stream invocation (--model, --resume, --allowedTools, --permission-mode, …). Anything we add is skipped if the user already specified it, which is why hasModelFlag/hasPermissionFlag exist.

The mid-session model switch Claude's model is fixed at spawn. Switching model mid-section therefore cannot be done in-band: we rewrite the stored resume request with the new model, tear the live process down, and let the next prompt respawn claude --resume <id> --model <new> and deliver itself. Codex, on the app-server, takes model and effort as turn parameters and needs none of this.

04Codex: app-server only

Codex used to run the obvious way: codex exec --json, one child process per turn, codex exec resume <threadId> to continue, idle inferred from process exit, and approvals hard-disabled with --ask-for-approval never. That path is gone. Today every Codex section runs on codex app-server — newline-delimited JSON-RPC over stdio.

One socket carries three message kinds, and the routing rule is the whole framing layer:

ShapeMeaning
{id, method, params}server→client request — we must answer it (approvals, user input)
{id, result|error}response to something we asked
{method, params}notification — the event stream

Layered on that: thread/start or thread/resume opens a section, turn/start runs a prompt, turn/steer injects one into a turn already in flight, turn/interrupt stops it. Streaming arrives as item/started, item/agentMessage/delta, item/completed, turn/completed, thread/tokenUsage/updated.

One shared client, not one per section

Threads already multiplex on a single app-server, so CodexAppServerSessionManager holds exactly one CodexAppServerClient for the whole app and maps each Panda section to a thread. Ten open Codex sections cost one process, not ten. The client is disposed when the last section goes idle.

What app-server bought us that exec could not

Approvals

The real prize

Server→client requestApproval requests are held open, surfaced as needs_action, and answered from the desktop panel — or from the phone, over the relay.

Streaming

Deltas, not blocks

item/agentMessage/delta gives the same live typing Claude's partial messages give.

Control

Steer and interrupt

First-class RPCs replace stdin tricks and process signals.

Truth

Real idle

turn/completed carries a status. Exit-code inference used to render a failed turn as a clean one.

Hard-won details A section is registered in the manager map synchronously, before the ~1.6 s thread/start handshake, because the renderer's first prompt arrives ~3 ms after start and used to fall through to a no-op. Prompts that arrive early go into a queue (not a single slot — a second prompt used to overwrite the first) drained at exactly one point. And turn/steer carries expectedTurnId, so we track a real turnActive window: turnId lingers after a turn ends, and losing the race falls back to a fresh turn.

05The convergence point

Everything above collapses into one reducer file, src/shared/stream-json.ts, and one state object:

  • applyStreamJsonEvent — folds a Claude stream-json event into StreamJsonState.
  • applyAppServerNotification — folds a Codex JSON-RPC notification into the same StreamJsonState.

Downstream of that line, nothing knows which vendor it is talking to. The renderer draws ConversationItem[]. The relay encrypts a snapshot. The phone renders the same items. Token accounting, turn duration footers, the section title, subagent nesting, pending approvals — all read from the one struct.

That is why adding app-server was a transport project and not a product rewrite: Phase 3 of the migration was explicitly "map ServerNotification → existing StreamJsonState so renderer + relay are untouched," and they were.

07The /btw sidecar

One place still spawns a one-shot: the /btw aside, a cheap side-question that must not disturb the running section. It is claude -p --output-format stream-json --verbose --include-partial-messages with the prompt as an argv, on a session id we control, usually on Haiku.

Its seeding rule is the interesting decision. Rather than --fork-session off the live session, the first question seeds a brand-new side session with the rendered transcript tail. Forking inherits Claude-specific context that goes stale across a Claude→Codex handoff and can trip auto-compaction on a long run; a transcript seed is runtime-agnostic and always current. Forking survives only as the fallback for a phone-issued ask that carries no transcript.

08Decision log

  1. Structured output over a PTY. The phone can only render what the desktop can describe. Chose stream-json before the mobile app existed, and it is the reason the mobile app was possible.
  2. Bidirectional stream-json for Claude. Keeping one process alive per section beats respawn-per-turn on latency and on session continuity; --resume becomes a recovery path, not the normal path.
  3. Best transport per vendor, one model internally. No lowest-common-denominator abstraction over the two CLIs. The abstraction lives at the state layer instead, where it costs one reducer and buys an untouched renderer and relay.
  4. App-server for Codex, and delete exec. Interactive approvals were unreachable from exec, and remote approval was already reserved in the protocol. Cutover completed 2026-07-30; the old builders were removed rather than left behind a flag, so there is exactly one Codex path to reason about.
  5. One shared app-server client. Threads multiplex; per-session processes would not have.
  6. Honest send results. A queued prompt reports success only if something will actually flush it — otherwise the renderer restarts the section instead of showing "Thinking…" forever.
  7. Let the model write the TL;DR. Both runtimes get the same instruction by whichever mechanism they support, rather than post-processing text in the app.

04 · Claude flags

Nothing on that line is decorative

  • --include-partial-messages — text streams into the bubble instead of landing in one block.
  • --include-hook-events — hook work is real waiting; hiding it looks like a hang.
  • --replay-user-messages — one authoritative ordering for the transcript, so the optimistic bubble reconciles instead of guessing.
  • --dangerously-skip-permissions — substituted for bypassPermissions, which headless Claude refuses at runtime. Gated behind Face ID in the UI.

The user's own typed flags survive through an allow-list; anything they set, we don't re-add.

07 · Scar tissue

Three bugs worth remembering

  • Register before you await. The renderer's first prompt lands ~3 ms after start; thread/start takes ~1.6 s. Registering after the handshake dropped it silently — thread open, no error, "Thinking…" forever.
  • A queue, not a slot. A second early prompt used to overwrite the first. One drain point now.
  • Steering has a precondition. expectedTurnId is checked server-side, and turnId lingers past the end of a turn — so track the live window and fall back to a new turn when you lose the race.

09 · The exception

/btw is still a one-shot

A cheap aside that must not disturb the running section: claude -p --output-format stream-json, prompt as argv, usually Haiku, on a session id we own.

It seeds from the rendered transcript tail, not --fork-session. Forking inherits Claude-specific context that goes stale across a Claude→Codex handoff and can trip auto-compaction on a long run. A transcript seed is runtime-agnostic and always current.

Forking survives only as the fallback when a phone-issued ask arrives with no transcript attached.

10 · Decisions

The seven that mattered

  • Structured output over a PTY — the phone can only render what the desktop can describe.
  • Bidirectional stream-json — one live process per section; --resume becomes recovery, not routine.
  • Best transport per vendor — abstract at the state layer, not the CLI layer.
  • App-server, and delete exec — approvals were unreachable otherwise; removed rather than flagged off.
  • One shared client — threads already multiplex.
  • Honest send results — never report a prompt sent that nothing will flush.
  • Let the model write the TL;DR — instruction, not post-processing.
